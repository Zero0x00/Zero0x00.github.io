OWASP Kubernetes Top 10 (2025): A Practical Guide

What each risk means, a command to check your own cluster for it, and how to fix it.

By Mohammad Arif · 10 min read

The OWASP Kubernetes Top 10 lists the most common ways clusters get compromised. This post goes through the 2025 edition one risk at a time. Each one has the same layout: what it is, how to check for it, and how to fix it. Where a risk is covered in depth in my Kubernetes series, I link to it.

K01: Insecure workload configurations

Pods run with more power than they need: as root, privileged, with host access, or with a writable filesystem. If an attacker gets code execution in such a Pod, escaping to the node is easy. This is the most common finding in real clusters.

Check

# Pods running privileged
kubectl get pods -A -o json | jq -r '.items[]
  | select(.spec.containers[].securityContext.privileged==true)
  | .metadata.namespace + "/" + .metadata.name'

# Scan manifests for risky settings
kube-linter lint ./k8s/
kubesec scan deployment.yaml

Fix

securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault
  • Do not use privileged: true, hostPath, hostNetwork, hostPID unless you can explain why.
  • Set CPU and memory limits, so one Pod cannot starve the node.
  • Enforce this for the whole namespace (see K04).

K02: Overly permissive authorization

RBAC rules that give users or ServiceAccounts more than they need: cluster-admin everywhere, wildcards (*), or powerful verbs. A stolen ServiceAccount token is only as dangerous as its role.

These permissions are almost as good as admin: create pods (can start a privileged Pod), get or list secrets, pods/exec, escalate, bind, impersonate.

Check

# Who is bound to cluster-admin?
kubectl get clusterrolebindings -o json | jq -r '.items[]
  | select(.roleRef.name=="cluster-admin")
  | .metadata.name + " -> " + ([.subjects[]?.name] | join(","))'

# What can this ServiceAccount do?
kubectl auth can-i --list --as=system:serviceaccount:prod:web -n prod

# Who can read secrets? (krew plugin)
kubectl who-can get secrets -n prod

Fix

  • Use namespaced Role and RoleBinding instead of ClusterRole where you can.
  • Give each app its own ServiceAccount with only the verbs and resources it uses. Never use the default one for real work.
  • Bind people through groups from your identity provider, and review bindings regularly.
  • Set automountServiceAccountToken: false on Pods that never call the API.

K03: Secrets management failures

Kubernetes Secrets are only base64-encoded, not encrypted. By default they sit in etcd in readable form, and anyone with get secrets permission can read them. Secrets also leak through Git repositories, environment variables printed in logs, and container images.

Check

# Long-lived token Secrets (should be rare)
kubectl get secrets -A --field-selector type=kubernetes.io/service-account-token

# Secrets committed to your repo
gitleaks detect --source .

Fix

  • Turn on encryption at rest for etcd (an EncryptionConfiguration, ideally with a KMS provider). On managed clusters, enable envelope encryption.
  • Limit who can get and list Secrets (K02).
  • Prefer an external secrets manager (Vault, AWS Secrets Manager, and so on) with the External Secrets Operator or the Secrets Store CSI driver.
  • Mount secrets as files rather than environment variables. Environment variables show up in kubectl describe, crash dumps and logs.
  • Never commit secrets to Git. If you must store them there, encrypt them first (SOPS, Sealed Secrets). Rotate anything that has leaked.

K04: Lack of cluster-level policy enforcement

Good practices that are only written in a document do not stop anyone. Without a policy that the cluster enforces, one team's mistake (a privileged Pod, an image from a public registry) goes straight through.

Check

# Is Pod Security Admission configured on your namespaces?
kubectl get ns --show-labels | grep pod-security

# Is a policy engine installed?
kubectl get pods -A | grep -Ei "kyverno|gatekeeper"

Fix

# Built in: enforce the "restricted" Pod Security Standard
kubectl label ns prod \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted
  • Add a policy engine (Kyverno or OPA Gatekeeper) or built-in ValidatingAdmissionPolicy for rules the built-in standard does not cover, such as "images only from our registry" or "resource limits required".
  • Start in warn or audit mode, fix what it reports, then enforce.
  • Check which namespaces are exempt. Attackers look for the namespace nobody covered.

K05: Missing network segmentation

By default, every Pod can talk to every other Pod, and out to the internet. One compromised Pod can then scan and attack everything else.

Check

# Namespaces with no NetworkPolicy at all
kubectl get networkpolicy -A
# Compare with: kubectl get ns

Fix

# Deny all traffic in the namespace, then allow only what is needed
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: prod
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  • Then add small allow rules per app: which Pods may call it, and where it may connect. Remember to allow DNS.
  • Control outbound (egress) traffic too. It limits data theft and command-and-control.
  • NetworkPolicies only work if your network plugin enforces them (Calico or Cilium do). Test that a blocked connection is really blocked.

K06: Overly exposed Kubernetes components

Control plane and node components reachable from places they should not be: an API server open to the internet, a kubelet that accepts anonymous requests, an etcd without authentication, an exposed dashboard, or an internal service published with a LoadBalancer or NodePort.

Check

# Services exposed outside the cluster
kubectl get svc -A | grep -E "LoadBalancer|NodePort"

# From outside your network (only on clusters you own):
nmap -p 6443,10250,2379 <node-or-api-ip>

Fix

  • Make the API server endpoint private, or restrict it to known IP ranges.
  • Kubelet: --anonymous-auth=false and --authorization-mode=Webhook.
  • etcd: accept connections only from the API server, with mutual TLS.
  • Do not expose the Kubernetes Dashboard or other admin UIs to the internet. Put them behind SSO and a VPN.
  • Review every LoadBalancer and NodePort Service. Use an Ingress with TLS for web apps.

K07: Misconfigured and vulnerable cluster components

Old Kubernetes versions, unpatched ingress controllers, container runtimes with known escapes, and insecure settings on the components themselves. Real examples include the runc escape CVE-2024-21626 and the ingress-nginx flaws known as IngressNightmare (CVE-2025-1974).

Check

# Versions of the cluster and nodes
kubectl version
kubectl get nodes -o wide

# Compare against the CIS Kubernetes Benchmark
kube-bench run

Fix

  • Stay on a supported Kubernetes version (roughly the latest three minor releases) and apply patch releases.
  • Patch what runs alongside Kubernetes: ingress controller, network plugin, container runtime, node OS, and add-ons.
  • Scan images of cluster components the same way as your own (Part 2).
  • Fix kube-bench findings. Many managed services handle the control plane for you, but node settings are still yours.

K08: Cluster to cloud lateral movement

A compromised Pod reaches the cloud account behind the cluster. The usual path: the Pod calls the node's metadata service (169.254.169.254) and gets the node's cloud credentials. If the node role is broad, the attacker now has access to storage, databases and other cloud services, well beyond the cluster.

Check

# From inside a test Pod: can it reach the metadata service?
kubectl run test --rm -it --image=curlimages/curl --restart=Never -- \
  curl -s -m 3 http://169.254.169.254/latest/meta-data/

If that returns data, any compromised Pod could do the same.

Fix

  • Give Pods their own cloud identity with workload identity (EKS Pod Identity or IRSA, GKE Workload Identity, Azure Workload Identity). Each ServiceAccount gets only the cloud permissions it needs.
  • Block the metadata service from Pods: a NetworkPolicy egress rule, and on AWS require IMDSv2 with a hop limit of 1.
  • Keep the node role minimal: just enough to join the cluster and pull images.

K09: Broken authentication mechanisms

Weak ways of proving who you are: shared kubeconfig files, static tokens, long-lived ServiceAccount token Secrets, client certificates (Kubernetes cannot revoke them), or anonymous access left on.

Check

# Can an unauthenticated user do anything?
kubectl auth can-i --list --as=system:anonymous
kubectl auth can-i --list --as=system:unauthenticated

# Legacy long-lived ServiceAccount tokens
kubectl get secrets -A --field-selector type=kubernetes.io/service-account-token

Fix

  • Log humans in with OIDC through your company SSO, with MFA. Do not hand out client certificates or shared kubeconfigs.
  • Use short-lived, automatically rotated ServiceAccount tokens (the default in current versions). Remove old token Secrets.
  • Disable anonymous authentication on the API server and kubelet unless you have a specific reason.
  • Remove access when people leave. With SSO this is one change.

K10: Inadequate logging and monitoring

If you cannot see what happened, you cannot detect an attack or investigate one. Many Kubernetes breaches are found by someone outside the company, weeks later.

Check

  • Are API server audit logs enabled, and can you search them?
  • Do container logs leave the node, or do they vanish when a Pod is deleted?
  • Would you get an alert if someone ran kubectl exec into a production Pod?

Fix

  • Enable audit logging, ship container and node logs to a central store, and alert on the events that matter.
  • Add runtime detection (Falco or Tetragon) for suspicious behavior inside containers.

A 30-minute audit

Run these on a cluster you own. They map to the risks above and show where you stand:

  1. kube-bench run for cluster settings (K07).
  2. The cluster-admin and can-i commands from K02, and kubectl who-can get secrets (K02, K03).
  3. kube-linter lint and trivy config on your manifests (K01).
  4. kubectl get networkpolicy -A and kubectl get ns --show-labels (K04, K05).
  5. kubectl get svc -A filtered for LoadBalancer and NodePort (K06).
  6. The metadata service test from K08.
  7. Ask: are audit logs on, and who gets the alerts? (K10)

What to fix first

  1. K06 and K09. Anything exposed to the internet, and weak ways to log in. These are the easiest for an attacker to find.
  2. K02 and K03. Over-broad RBAC and unprotected Secrets. They decide how bad a single compromise gets.
  3. K01, K04 and K05. Lock down workloads, enforce it with policy, and segment the network, so one Pod cannot reach everything.
  4. K08. Cut the path from the cluster to your cloud account.
  5. K07 and K10. Keep patching, and make sure you can see what is happening.
