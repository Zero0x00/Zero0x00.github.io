Monitoring, Logging and Runtime Security

Prevention will fail sometimes. This part is about seeing the attack while it happens, and knowing what to do next.

By Mohammad Arif · 9 min read · Part 1 · Part 2

Part 1 explained how the cluster works. Part 2 reduced the chance of running something bad. But a new vulnerability, a stolen credential or a policy mistake can still let an attacker in. If you have no logs and no detection, you will not know until the damage is done, and you will have nothing to investigate with. Many breaches go unnoticed for weeks for exactly this reason.

1. Four places to watch

Each layer of a cluster can show you something different. An attacker usually touches more than one.

LayerWhat it tells you
Control plane (audit logs)Every request to the API server: who did it, what they did, and whether it was allowed.
NodeLogins to the node, kubelet activity, kernel messages.
ContainersApplication logs, and what the container is actually doing: processes started, files opened, network connections.
NetworkWhich Pods and external addresses are talking to each other.

2. Kubernetes audit logs

The API server sees every change and every read of the cluster, so its audit log is the most useful single source. It records the user or ServiceAccount, the action, the resource, the time, the source IP, and the result. You choose how much detail to keep with an audit policy.

apiVersion: audit.k8s.io/v1
kind: Policy
rules:
# Secrets: log who touched them, never the contents
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets", "configmaps"]
# Someone running a command inside a Pod: keep full detail
- level: RequestResponse
  resources:
  - group: ""
    resources: ["pods/exec", "pods/attach"]
# Permission changes: keep full detail
- level: RequestResponse
  resources:
  - group: "rbac.authorization.k8s.io"
# Everything else: who, what, when
- level: Metadata

Rules are checked in order and the first match wins, so the general rule goes last. Do not log Secrets at Request or RequestResponse level, because the secret values would then be written into the log.

On a managed service, you turn this on instead of writing the policy file: EKS control plane logging, GKE audit logs, or AKS diagnostic settings. Check that it is actually enabled, because it is often off by default.

What to alert on

  • pods/exec or pods/attach: someone ran a command inside a Pod. Normal for an admin, suspicious from a ServiceAccount.
  • A new Pod with privileged: true, hostPath, hostNetwork or hostPID.
  • A new RoleBinding or ClusterRoleBinding, especially to cluster-admin.
  • get or list on Secrets by a user or ServiceAccount that does not normally do that.
  • Requests from system:anonymous, or many 403 Forbidden results in a short time (someone is probing what they can do).
  • Changes in kube-system.

3. Cluster logging

Kubernetes does not keep container logs for you. kubectl logs reads a file on the node, and that file disappears when the Pod is deleted or the node is replaced. An attacker who wants to hide will do exactly that. So logs must be copied off the node quickly.

  • Run a log agent on every node (Fluent Bit, Vector, or similar) as a DaemonSet. It reads container output and sends it to a central store.
  • Use a central store that you can search and alert on: Loki, OpenSearch or Elasticsearch, or your cloud's logging service.
  • Collect audit logs, node logs and application logs in the same place, so you can follow one event across layers.
  • Keep logs long enough to investigate. Attacks are often found weeks later. Make the log store write-only for the workloads that produce logs, so a compromised Pod cannot erase its own tracks.
  • Keep clocks in sync (NTP), or you cannot put events in order.

Application logs

Have your apps log logins, failed logins, permission denials and other important actions in a structured format such as JSON. Never log passwords, API keys or tokens. If a JWT or session token ends up in a log, anyone who can read the logs can use it (see my JWT security post).

Metrics

Prometheus and Grafana are mostly for reliability, but they also catch attacks. A sudden CPU spike in a Pod that is normally idle can be cryptomining. Unexpected restarts, new Pods in system namespaces, and a jump in outbound traffic are all worth an alert.

Network

Start with NetworkPolicies that deny traffic by default and allow only what each app needs, including limits on outbound (egress) traffic. Then collect flow logs (cloud VPC flow logs, or Cilium Hubble) so you can see who talked to whom. Outbound connections to unknown addresses are a common sign of data theft or a command-and-control channel.

4. Runtime security

Logs tell you what the API server and the apps recorded. They do not tell you what is happening inside a container. Runtime security tools watch the kernel for that: which processes start, which files are opened, which connections are made. They compare it against rules for suspicious behavior and raise an alert.

ToolWhat it is
FalcoThe most widely used open-source runtime detection tool (a CNCF project). Runs on each node and ships with a default set of rules. You write your own in YAML.
TetragoneBPF-based, from the Cilium project. Can detect, and also block, behavior in the kernel.
TraceeeBPF-based detection from Aqua Security.

Typical things these tools catch:

  • A shell started inside a container that should only run one program.
  • A process reading /etc/shadow or the ServiceAccount token file.
  • A package manager or download tool run inside a running container.
  • Writes to system directories such as /bin or /etc.
  • A container using the host's namespaces, or mounting sensitive host paths.
  • Outbound connections to places the container has never contacted before.

A simple Falco rule looks like this. Falco's default rules already include something similar, so treat this as an illustration:

- rule: Shell in container
  desc: A shell was started inside a container
  condition: spawned_process and container and proc.name in (bash, sh, zsh)
  output: Shell started in container (user=%user.name container=%container.name image=%container.image.repository command=%proc.cmdline)
  priority: WARNING

This is why Part 2 pushed for small images. A distroless image has no shell at all, so an attacker has fewer tools to use, and any shell that does appear stands out.

Expect noise. Out of the box, runtime tools will alert on normal behavior in your apps. Run them in a quiet mode first, tune the rules for your workloads, and then send only the important alerts to people. An alert channel that everyone ignores is worse than none.

Limit what an attacker can do, too

Detection works better when the container is already locked down. These settings in the Pod spec remove most of what attackers rely on:

securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault

Kubernetes can enforce these across a namespace with Pod Security Admission, using the restricted level. Also turn off the automatic ServiceAccount token for Pods that do not call the API (automountServiceAccountToken: false).

5. Seeing the whole attack

Remember the attack chain from Part 1. Figure 2 shows where each step leaves a trace. No single source catches all of it, which is why you need several.

6. When an alert fires

Say a Pod is showing a shell and a read of the token file. Do not just delete it. Deleting destroys the evidence and the attacker may already have moved on. A calmer order:

  1. Confirm. Check the audit logs and runtime events. Is this a real attack, or an admin debugging?
  2. Contain. Cut it off without deleting it. Apply a NetworkPolicy that blocks the Pod's traffic, or remove its label so Services stop sending it traffic. If it may have escaped, cordon the node so nothing new is scheduled there.
  3. Collect. Save the Pod's logs, its spec, and if you can, a copy of its filesystem or memory, before anything is removed. Make sure the central logs from the time window are kept.
  4. Find the reach. Use the audit log to see what that Pod's ServiceAccount did. What could it read? Which Secrets did it touch?
  5. Rotate. Replace every credential the Pod could access: ServiceAccount tokens, Secrets, database passwords, API keys.
  6. Recover and fix. Redeploy from a known-good image, patch the entry point, and add a detection or policy so this exact path is caught earlier next time.

Write this down and practice it once before you need it. During an incident, nobody wants to learn what the audit log looks like for the first time.

Where to start

  1. Turn on API audit logs and send them somewhere you can search. Add the alerts from section 2.
  2. Ship container and node logs off the node with a DaemonSet agent.
  3. Add default-deny NetworkPolicies and apply the restricted Pod security level.
  4. Install Falco (or Tetragon), tune it, then alert on the few rules that matter.
  5. Write and test an incident checklist.
