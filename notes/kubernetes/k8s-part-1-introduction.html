How Kubernetes Works

Architecture, how a request flows, and the core objects, with diagrams.

By Mohammad Arif · 9 min read

You cannot secure Kubernetes well without knowing how it works. This part covers the basics that Parts 2 and 3 build on, and notes why each piece matters for security.

1. The problem Kubernetes solves

A container packages an app with everything it needs to run. Running one is easy. Running hundreds across many machines is not:

  • Which machine should each container run on?
  • What happens when a container or a whole machine dies?
  • How do you roll out a new version without downtime, and roll it back if it breaks?
  • How do containers find and talk to each other when their IPs keep changing?
  • How do you scale up under load and back down afterwards?

Kubernetes (K8s) is a container orchestrator that handles all of this. You describe what you want ("run 3 copies of this image and expose port 80"), and Kubernetes keeps working to make the cluster match. It constantly compares the desired state with the actual state and fixes any difference. Most of what follows is built on that idea.

2. Cluster architecture

A cluster has a control plane, which makes decisions, and worker nodes, which run your apps.

Control plane

  • kube-apiserver: the REST API and the only entry point. kubectl, controllers, the scheduler and kubelets all go through it. It authenticates, authorizes and validates every request, and is the only component allowed to read and write etcd.
  • etcd: a consistent key-value store holding the full cluster state: every Pod, Secret, ConfigMap and RBAC rule.
  • kube-scheduler: watches for Pods with no node and assigns each one to a node based on resources, affinity rules, taints and tolerations.
  • kube-controller-manager: runs control loops. The ReplicaSet controller notices "3 wanted, 2 running" and creates another Pod. The node controller notices a node went silent.

Worker node

  • kubelet: the node agent. It watches the API server for Pods assigned to its node, tells the container runtime to start them, runs health probes, and reports status back.
  • Container runtime: containerd or CRI-O. This is what actually pulls images and runs containers.
  • kube-proxy: programs the node's network rules so traffic to a Service reaches one of its Pods.

3. What happens when you run kubectl apply

Every change goes through the same steps. Knowing them shows where you can add security controls.

  1. Authentication: the API server identifies the caller from a client certificate, bearer token (including ServiceAccount tokens), or an OIDC identity.
  2. Authorization: RBAC decides whether that identity may perform this verb (create, get, delete) on this resource in this namespace.
  3. Admission: mutating admission controllers can modify the object (inject a sidecar, set defaults). The request is then validated against the schema, and validating admission controllers can reject it. This is where Pod Security Admission and policy engines such as Kyverno or OPA Gatekeeper enforce rules like "no privileged containers".
  4. Persist: the object is written to etcd as desired state.
  5. Reconcile: controllers, the scheduler and kubelets notice the change and act on it, always by reading and writing through the API server.

RBAC controls who can create objects. Admission controls what those objects can contain. Someone allowed to create Pods can still be blocked from creating a privileged Pod, but only if an admission policy is in place.

A minimal example

Two objects: a Deployment that runs three copies of an app, and a Service that exposes them inside the cluster.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
      - name: web
        image: registry.example.com/web:1.4.2
        ports: [{ containerPort: 8080 }]
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector: { app: web }
  ports: [{ port: 80, targetPort: 8080 }]

Delete one of the three Pods and the ReplicaSet creates a replacement within seconds. That self-healing is the control loop from section 1 at work. This manifest also has security gaps: no securityContext, no resource limits, and an image tag instead of a digest. The next parts cover how to fix them.

5. Risky defaults

A few defaults explain many real cluster compromises:

  • The network is flat. Without NetworkPolicies, any Pod can connect to any other Pod, and to the node's metadata service.
  • Every Pod gets a ServiceAccount token unless you opt out, and it works against the API server.
  • Secrets are not encrypted at rest by default. Anyone who can read etcd, or a backup of it, reads them all.
  • Containers share the node's kernel. A container escape lands on the node, and from there on every Pod scheduled to it.
  • Everything is a manifest. One over-broad RBAC binding or one malicious manifest can affect the whole cluster.

These often combine into one attack. The attacker exploits a vulnerable app in a Pod, reads the mounted ServiceAccount token, uses an over-privileged role to create a privileged Pod, escapes to the node, and then reaches other workloads and Secrets. A control at any of these steps can stop it.
