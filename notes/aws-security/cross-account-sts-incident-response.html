Investigating and Containing Compromised AWS STS Credentials Across Accounts

A worked incident: trace a bulk S3 download back to a session using one account's logs, then stop it without taking down the services that share the role.

By Mohammad Arif · 14 min read

An alert says a large number of objects were downloaded from a sensitive S3 bucket. The activity used a role assumed from another AWS account, and the temporary credentials are still valid. This post covers two questions an incident commander will ask: what happened, and can we stop it right now without causing an outage? The answers depend on knowing exactly what AWS logs prove and what IAM changes actually affect.

1. The scenario

  • Your company uses several AWS accounts under AWS Organizations.
  • An application on an EC2 instance in Account A has an IAM role (AppRole) that is allowed to assume a role in Account B.
  • The role in Account B, ProductionDataReader, can read a sensitive S3 bucket. Five other production services also use it.
  • An alert shows a large download from the bucket. The team suspects the EC2 instance was compromised and that its credentials were used to assume the role.
  • You can see CloudTrail and IAM in Account B only. You cannot see Account A.
  • The attacker's temporary credentials have about 45 minutes left.

2. Evidence: what logs prove, suggest and leave unknown

Keep these three apart in everything you write down. Mixing them up is how incident reports turn into guesses.

LevelExamples here
ProvesA specific STS session made specific API calls, at specific times, from a specific source IP and user agent.
SuggestsWhere the activity came from (a network, a tool such as the AWS CLI or a Python SDK), and which workload owned the credentials.
UnknownWhich process or person used the credentials, whether they were stolen or misused by an insider, and what else the attacker did outside the logs you can see.

3. Investigation, step by step

Start from what you know for sure (the suspicious S3 activity) and work backward to the identity. Do not start by searching for AssumeRole and hoping.

Step 0: Check that the evidence exists

CloudTrail records S3 object-level actions such as GetObject only if data events are enabled for the bucket. They are off by default. Without them you can see who assumed the role, but not which objects were read. Alternatives are S3 server access logs (if enabled) and GuardDuty S3 findings. Find out in the first minutes what you have, because it decides how well you can measure the damage.

Step 1: Read the S3 events

Look at the GetObject events for the bucket in the alert window and pull out the session identity:

FieldWhat it tells you
userIdentity.type, arnAn assumed-role session: arn:aws:sts::<account>:assumed-role/ProductionDataReader/<session-name>
userIdentity.accessKeyIdThe temporary access key (starts with ASIA). This is the key you will follow.
userIdentity.sessionContextThe role that was assumed, and when the session was created
sourceIPAddress, userAgentWhere the request came from and what tool made it
requestParameters (bucket, key)Which objects were read
eventTimeWhen it started, how fast, and whether it is still going
-- Athena over CloudTrail logs (adjust names to your table)
SELECT eventtime, sourceipaddress, useragent,
       useridentity.accesskeyid,
       json_extract_scalar(requestparameters, '$.key') AS object_key
FROM cloudtrail_logs
WHERE eventsource = 's3.amazonaws.com'
  AND eventname = 'GetObject'
  AND useridentity.sessioncontext.sessionissuer.arn LIKE '%role/ProductionDataReader'
  AND eventtime > '2026-11-04T17:00:00Z'
ORDER BY eventtime;

Group the results by accessKeyId and sourceIPAddress. Five legitimate services and one attacker will usually form separate groups. The suspicious one is the key with the unusual IP, user agent, volume or object pattern.

Step 2: Link the key to its AssumeRole event

Now find the STS call that created that key. In Account B, the AssumeRole event includes:

FieldUse
responseElements.credentials.accessKeyIdThe link. Match it to the accessKeyId in the S3 events. This is exact, unlike matching by time or IP.
userIdentity (the caller)The calling account and principal, and the caller's own access key
requestParameters.roleArn, roleSessionNameWhich role, and the session name the caller chose
sourceIdentity (if used)A name that stays attached to the session, set at assume time
sourceIPAddress, userAgentNetwork origin and tool for the assume call
responseElements.credentials.expirationWhen the credentials die. Tells you how long you have.

Do not link events by IP address or timestamp alone. Several sessions can share a NAT gateway, and many sessions can start in the same minute. The access key ID is the key.

Step 3: Work out who called, and what that does and does not prove

The caller's identity shows the source account (Account A) and the principal that assumed the role. For credentials from an EC2 instance profile, the session name is normally the instance ID, so the event may name the instance whose credentials were used. That is a strong lead.

It is still not proof of who acted. Credentials can be copied off an instance and used from anywhere. Compare the sourceIPAddress in the assume call with the instance's known public or NAT address (from Account A):

  • It matches: the activity probably came from or through that network. It could still be an attacker on the instance, or another workload behind the same NAT.
  • It does not match: the credentials were likely taken from the instance and used elsewhere.

An IP address is a network location, not an identity. It can belong to a NAT gateway, proxy, VPN or other shared infrastructure.

Step 4: Scope everything that key did

Search all events for that access key ID, in all services and regions, not only S3:

  • Other buckets, ListBucket calls, and other services the role can reach.
  • Further AssumeRole calls (role chaining into other accounts).
  • IAM changes or attempts to create persistence.
  • The earliest activity from that caller or IP, to find when it started.

Write down the object list, count and bytes read. Legal and privacy teams will need the exact scope, and it is only as good as the logging you confirmed in Step 0.

Can Account B alone identify the instance or the attacker?

Partly. Account B can tell you the calling account, the calling role, usually the session name (often the instance ID), the source IP and the tool. It cannot tell you what ran on the instance, who the attacker is, or how they got the credentials. For that you need Account A: its CloudTrail, GuardDuty findings, VPC flow logs, EC2 inventory and logs from the host itself.

4. Containment: stop it without an outage

The credentials still have 45 minutes left and five legitimate services use the same role. First, the facts that decide what works.

Changing the trust policy does not stop existing sessions

The trust policy controls who can assume the role. Tightening it blocks new assumptions only. Credentials already issued keep working until they expire (an hour by default, up to the role's maximum session duration). Tightening the trust policy is worth doing to stop the attacker getting fresh credentials, but it does nothing about the session they already hold.

Your options

MechanismWhat it doesTrade-off
Change the trust policyStops new role assumptionsExisting credentials keep working
Targeted explicit denyBlocks one session using an identity conditionNeeds an attribute that uniquely identifies the bad session
Deny by aws:TokenIssueTimeBlocks every session issued before a cutoff timeAlso blocks legitimate sessions issued before the cutoff until they refresh
S3 bucket policy explicit denyProtects the data immediately, whatever the roleCan block real applications if too broad. Keep an admin exception.
Network conditions (IP, VPC endpoint)Limits requests to approved network pathsFails if the attacker shares an approved path
Delete the roleRemoves the accessCauses the outage you were trying to avoid, and loses configuration you need

Option 1: Deny the specific session

If the bad session can be told apart from the good ones, deny just that. For an assumed-role session, aws:userid has the form <role-id>:<session-name>, so a unique session name works. aws:SourceIdentity and session tags can work too, if you set them up beforehand.

{
  "Effect": "Deny",
  "Action": "*",
  "Resource": "*",
  "Condition": {
    "StringLike": { "aws:userid": "AROAEXAMPLEROLEID:suspicious-session-name" }
  }
}

This only works if the attribute is genuinely unique. The caller chooses the session name. If legitimate services use the same name (for example a default like app), a deny on it would cut them off as well. Check the real values in CloudTrail before relying on this.

Option 2: Deny everything issued before a cutoff

If you cannot isolate the session, deny all sessions issued before a chosen time. The condition key aws:TokenIssueTime records when the temporary credentials were created.

{
  "Effect": "Deny",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::sensitive-data/*",
  "Condition": {
    "DateLessThan": { "aws:TokenIssueTime": "2026-11-04T18:00:00Z" }
  }
}

Walk through three sessions with a cutoff at 18:00 UTC:

SessionIssuedResult
Attacker17:30Denied. Issued before the cutoff.
Service A17:45Denied. Issued before the cutoff, even though it is legitimate.
Service B18:15Not affected by this statement. It still needs permission from the rest of the policies.

Two limits you must state out loud:

  • Scope. The example above denies only s3:GetObject on one bucket. The attacker's credentials can still call DynamoDB, other buckets or other APIs the role allows. During an active incident, widen it to "Action": "*" for old sessions, or review what else the role can do. The IAM console's "Revoke active sessions" button does the wide version by attaching a deny policy for sessions issued before now.
  • Collateral. Every legitimate session issued before the cutoff is blocked until it gets new credentials. Whether that is an outage depends on how each service refreshes.

The safe order for the legitimate services

  1. List the workloads that use the role and how each gets its credentials.
  2. Have them obtain fresh sessions after the cutoff: through their normal credential refresh, or a controlled restart where needed.
  3. Verify in CloudTrail that new AssumeRole events appeared with creation times after the cutoff, and check application health.
  4. Apply the deny. IAM changes are eventually consistent, so allow a short time for them to take effect.
  5. Confirm the attacker's access key now gets AccessDenied in CloudTrail and the services are still healthy.

If data is leaving right now, containment comes first. Apply the deny, or restrict the bucket, immediately, and accept a short, planned disruption. Agree this with the incident commander and the service owners. A disruption-free rollout is not worth more confidential data being downloaded.

The fast, narrow option: protect the bucket

An explicit deny in the bucket policy protects the data at once and does not depend on the role. For example, deny GetObject except for approved roles and expected network paths, and keep an exception for incident responders so you do not lock yourself out. It buys time while you work out the precise session deny.

What about IP and network restrictions?

They can help as an extra layer, but do not rely on them:

  • If the attacker works through the same compromised instance or the same NAT gateway as legitimate traffic, an IP allowlist lets them through.
  • Production services may reach AWS through VPC endpoints, not fixed public IPs. Use aws:SourceVpce or aws:SourceVpc for those. aws:SourceIp does not apply to requests that come through a VPC endpoint.
  • Adding legitimate IPs one at a time while watching for failures, during an incident, risks outages and mistakes. Establish the real network paths first, in advance if you can.

If you cannot tell the attacker from legitimate sessions

Then no precise deny exists. Stop the exfiltration first (bucket-level deny or the cutoff deny), accept a controlled disruption, and rebuild the legitimate services' access in the right order afterwards.

5. Contain the source in Account A

You cannot see Account A, but you can ask its owners to act:

  • Isolate the instance. Swap its security group for one with no outbound access. Do not terminate it, because you need its disk and memory for forensics. Snapshot its volumes.
  • Revoke the role's sessions in Account A only after isolating the host. A running instance fetches fresh credentials from its metadata service. If the attacker is still on the host, revoking first just hands them new credentials.
  • Find the way in. Common causes are a web flaw that reaches the instance metadata service (SSRF), remote code execution, or a leaked key. Fix that cause.
  • Rotate every secret that was on the instance or reachable from it, and check other instances that use the same role.
  • Look for GuardDuty findings about instance credentials being used from another network.

6. Make the next incident easier

  • Turn on S3 data events (or server access logs) for sensitive buckets before you need them.
  • Give each service its own role and a distinct, meaningful session name. A shared role like ProductionDataReader is what made this containment hard.
  • Require sts:SourceIdentity on cross-account role assumption, so sessions carry a name that cannot be changed later.
  • Restrict the trust policy to specific principals and your organization (aws:PrincipalOrgID).
  • Keep session durations short.
  • Require IMDSv2 on instances, with a hop limit of 1, to make metadata credential theft harder.
  • On sensitive buckets, require access through a VPC endpoint and named roles.
  • Alert on AssumeRole from unusual IPs or tools, and on unusual download volume.
  • Send CloudTrail to a separate log archive account with log file validation enabled.
  • Write and practice the containment steps above, so nobody learns IAM behavior during an incident.

7. Briefing the incident commander

Use this order: decision, mechanism, verification, impact. For example:

"I would deny the compromised session in Account B now. I identified it from the S3 events by its access key and linked it to the AssumeRole call. Its session name is shared with a legitimate service, so I can't deny it individually. Instead I'll deny all sessions issued before 18:00, which also blocks the five services until they refresh. They need to restart or refresh their credentials, which the owners can do in about ten minutes. Because data is still leaving, I recommend applying the deny first and accepting that short disruption. Afterwards I'll confirm the attacker's key gets AccessDenied and that the services are healthy. In parallel, Account A's owners should isolate the instance and preserve its disk."

8. Things that sound right but are not

What you hearWhy it is not enough
"Update the trust policy to stop them."It only blocks new assumptions. Existing sessions keep working.
"Rotate the role."A role has no password to rotate. You can cut off existing sessions or force new ones.
"Block the attacker's IP."They can change network. The IP may also be shared with legitimate traffic.
"That IP is our EC2 instance, so the instance did it."An IP is a location. Credentials can be used from elsewhere, and addresses are often shared.
"Delete the role."It causes the outage and removes evidence of how it was configured.
"Our alert will tell us if it happens again."Detection does not undo a download that already happened.

Summary

  • Start from the known S3 activity, then link it to the STS session by access key ID, not by IP or time.
  • Say clearly what the logs prove, what they suggest, and what is unknown.
  • Changing a trust policy does not end sessions already issued.
  • Use a targeted deny only when an attribute is truly unique. Otherwise use a cutoff deny with aws:TokenIssueTime, and know its scope and collateral damage.
  • If data is actively leaving, stop it first and coordinate the disruption.
  • Contain the source in Account A, but isolate the host before revoking its role.
