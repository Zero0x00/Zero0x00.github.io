SQL Injection in Practice: Values, Column Names, Stored Data and Stored Procedures

Most people learn "use placeholders" and stop there. This post covers the cases where that advice is not enough, with code you can read and test yourself.

By Mohammad Arif · 14 min read

This post is for developers and reviewers who have heard "use parameterized queries" and want to know what that does and does not cover. We start from the basics and build up. Each section adds one idea that the next one needs: first how injection works, then why values and column names need different fixes, then data that is stored and used later, and finally database functions. The examples use Python and PostgreSQL, but the ideas apply to any language and database.

1. How SQL injection works

A SQL query is a text command sent to the database. If you build that text by joining strings, user input becomes part of the command:

query = f"SELECT * FROM employees WHERE department = '{department}'"

With a normal value, Finance, the database receives:

SELECT * FROM employees WHERE department = 'Finance'

But the database cannot tell which part of that text is your code and which part came from the user. If the user sends x' OR '1'='1, the database receives:

SELECT * FROM employees WHERE department = 'x' OR '1'='1'

The quote in the input closed the string early, and the rest became SQL. The condition is now always true, so every row comes back. That is SQL injection: input that was meant to be data is read as part of the command.

The fix idea is to send the command and the data separately, so the database never has to guess. That is what a parameterized query (also called a prepared statement) does:

cursor.execute("SELECT * FROM employees WHERE department = %s", (department,))

The %s is a placeholder. The value travels separately and is always treated as a value. The same hostile text now just searches for a department with a strange name and finds nothing.

2. The code we will review

Here is a reporting endpoint for an internal analytics tool:

@app.get("/api/reports")
def get_report(request):
    department = request.args.get("department")
    sort_by = request.args.get("sort_by", "created_at")

    query = f"""
        SELECT id, employee_name, salary, department
        FROM employees
        WHERE department = '{department}'
        ORDER BY {sort_by}
    """
    return database.execute(query)

The developer says: "This API is internal and needs SSO. The department comes from a dropdown. We also block words like UNION and DROP." Each of these three claims fails:

  • SSO only proves who is logged in. Any employee, or anyone with a stolen session, is logged in. Authentication does not clean input.
  • A dropdown is a user interface, not a control. The browser sends a normal HTTP request, and anyone can edit it. In this code request.args reads the URL query string (/api/reports?department=Finance&sort_by=salary), which a user can change in the address bar.
  • Keyword blocklists are easy to get around. SQL has many ways to say the same thing, different capitalization, comments, and alternatives to the blocked word. A blocklist tries to guess what attackers will write. Separating code from data removes the guesswork.

3. Two injection points, two different fixes

This query has two places where input is pasted in, and they are not the same kind of thing.

  • department sits inside quotes and is a value. A placeholder can stand in for a value.
  • sort_by sits after ORDER BY and is an identifier, meaning the name of a column (or a table). It is part of the structure of the query, like a word in a sentence, not a piece of data. A placeholder cannot stand in for it.

Both are vulnerable, but the fixes differ. This is the most common gap in code reviews, so we take them one at a time.

Fix for the value: a placeholder

cursor.execute(
    "SELECT id, employee_name, salary, department FROM employees WHERE department = %s",
    (department,),
)

The value is passed separately, so it cannot change the shape of the query.

Fix for the identifier: an allowlist

A user cannot be trusted to name a column, because there is no safe way to quote their text into the structure of the query. Instead, you decide which columns are allowed, and let the user pick from your list:

ALLOWED_SORT_COLUMNS = {
    "name": "employee_name",
    "department": "department",
    "date": "created_at",
}

sort_by = request.args.get("sort_by", "date")
column = ALLOWED_SORT_COLUMNS.get(sort_by)
if column is None:
    raise ValueError("Invalid sort column")

query = f"""
    SELECT id, employee_name, salary, department
    FROM employees
    WHERE department = %s
    ORDER BY {column}
"""
cursor.execute(query, (department,))

The only text pasted into the SQL is column, which comes from a dictionary you wrote, never from the request. A sort_by that is not in the dictionary is rejected. The same approach works for sort direction: map the user's choice to a literal ASC or DESC.

Some libraries can quote identifiers for you, for example psycopg2.sql.Identifier. That is safe from injection, but it will happily sort by any column the user names, including ones you did not mean to expose. An allowlist also decides which columns are allowed, so it is the better default for user-chosen sorting.

4. A fix that looks right but breaks the feature

A well-meaning developer sends a pull request that puts placeholders everywhere:

query = """
    SELECT id, employee_name, salary, department
    FROM employees
    WHERE department = %s
    ORDER BY %s
"""
cursor.execute(query, (department, sort_by))

They say: "Both inputs are placeholders, so the query is fully parameterized and SQL injection is fixed." Should you approve it?

First, is it still injectable? No. The value is bound as data, so it cannot change the SQL structure. Second, does it work? Also no. A placeholder carries a value. When you pass the text "salary", you get a text value, not the salary column. What happens next depends on the driver and the database:

  • If the driver fills in the value on the client (psycopg2 does), the database sees ORDER BY 'salary'. PostgreSQL rejects a plain non-integer constant in ORDER BY with an error. (An integer such as ORDER BY 2 means "the second output column", which is a different surprise.)
  • If the value is bound on the server side as a real parameter, the query can run and sort by a constant, which means the sort silently does nothing.

So the fix is safe but the feature is broken, and one of the outcomes is worse than an error because it fails silently. This matters in practice: a security fix that breaks a feature often gets reverted, and the revert goes back to string concatenation. Reject the pull request, explain the value versus identifier difference, and offer the allowlist version from section 3.

5. Second-order SQL injection

So far the input went straight from the request into the query. Second-order injection is different: the attacker's text is stored first and used later.

Say users can name their reports, and the app stores the name safely with placeholders:

def create_report(name, owner_id):
    cursor.execute(
        "INSERT INTO reports (name, owner_id) VALUES (%s, %s)",
        (name, owner_id),
    )

Days later, a background job reads that name and builds another query:

def run_saved_report(report_id):
    cursor.execute("SELECT name FROM reports WHERE id = %s", (report_id,))
    report_name = cursor.fetchone()[0]

    query = f"""
        SELECT * FROM analytics
        WHERE report_name = '{report_name}'
    """
    cursor.execute(query)

The developer's reasoning: "We used placeholders when saving, and the job only reads from our own database, so it is trusted." That reasoning is the trap.

Data does not become trustworthy because it passed through your database, a queue, a cache or an internal API. What matters is how each query uses it.

Do not try to fix this by cleaning the name when it is saved. A report named Director's Quarterly Report is perfectly valid, and the apostrophe is not an attack. Keep the data as it is, and make sure every query that uses it treats it as a value:

cursor.execute(
    "SELECT * FROM analytics WHERE report_name = %s",
    (report_name,),
)

The stored text can now contain any characters and it stays data.

6. Stored procedures are not automatically safe

A stored procedure (or database function) is code that runs inside the database. Teams sometimes move queries there and say "the app calls a procedure with a placeholder, so injection is fixed". Look at what the function does with the value:

CREATE FUNCTION search_employees(p_department TEXT)
RETURNS SETOF employees AS $$
DECLARE
    query TEXT;
BEGIN
    query := 'SELECT * FROM employees WHERE department = ''' || p_department || '''';
    RETURN QUERY EXECUTE query;
END;
$$ LANGUAGE plpgsql;
cursor.execute("SELECT * FROM search_employees(%s)", (department,))

The Python call is safe, so the value reaches the function intact. But inside the function, || joins strings together and EXECUTE runs the result as a new query. That is the same string-building mistake from section 1, moved one layer down. Binding the arguments of the call protects the call. It does not protect dynamic SQL built inside the function.

Fixing the function

Best: do not use dynamic SQL when you do not need it.

CREATE FUNCTION search_employees(p_department TEXT)
RETURNS SETOF employees AS $$
BEGIN
    RETURN QUERY
    SELECT * FROM employees e WHERE e.department = p_department;
END;
$$ LANGUAGE plpgsql;

If you really need dynamic SQL, pass values with EXECUTE ... USING so they stay values:

RETURN QUERY EXECUTE
    'SELECT * FROM employees WHERE department = $1'
    USING p_department;

For a dynamic column or table name inside a function, use PostgreSQL's format() with %I, which quotes an identifier safely (and %L for a literal). Even then, prefer picking from a fixed list.

Why SECURITY DEFINER raises the stakes

By default a function runs with the caller's database permissions (SECURITY INVOKER). A function declared SECURITY DEFINER runs with the permissions of the role that owns it. This is useful when you want to give controlled access to data the caller cannot read directly. It also means that if the function is injectable, the attacker's SQL runs with the owner's permissions, which are often much higher than the app's.

ModeRuns withIf the function is injectable
SECURITY INVOKER (default)The caller's permissionsDamage is limited to what the app account can already do
SECURITY DEFINERThe function owner's permissionsThe attacker may reach what the owner can reach

A fixed function can still be risky

Suppose we make the function static (no dynamic SQL) and mark it SECURITY DEFINER. Is it still vulnerable to SQL injection through p_department? No, because the value is never part of the SQL text. But other risks remain, and they come from the elevated permissions:

  • It may expose more than the caller should see. If the owner can read the whole table and the app account cannot, any caller can now read every department. That function is an access control decision, so it needs its own authorization.
  • search_path hijacking. The function finds employees by searching schemas in order. If an untrusted user can create objects in a schema searched earlier, they can place a look-alike object there and trick the function into using it. The PostgreSQL docs say to set search_path on SECURITY DEFINER functions, with pg_temp last, for this reason.
  • Who can call it. By default, execute permission on a new function is granted to PUBLIC (everyone). Revoke it and grant it only to the roles that need it.
  • An over-powered owner. Make the owner a role with only the rights the function needs, not a superuser or an admin account.
BEGIN;
CREATE FUNCTION search_employees(p_department TEXT)
RETURNS SETOF employees AS $$ ... $$
LANGUAGE plpgsql SECURITY DEFINER
SET search_path = public, pg_temp;
REVOKE ALL ON FUNCTION search_employees(TEXT) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION search_employees(TEXT) TO report_app;
COMMIT;

7. Fixing injection does not fix access control

A perfectly safe query can still return data the user should not see. In our example the report returns salary for a department the caller picks. If the user is not allowed to see salaries, parameterized queries do not help. Injection controls answer "can the user change my query?". Authorization answers "should this user get this data?". You need both, and the access control post covers the second one.

8. How to test it safely

Only test systems you own or have permission to test, and use a staging database filled with fake data, never real salaries.

  • Record the normal behavior first: a real department and a real sort option.
  • Test department and sort_by separately, since one is a value and one is an identifier.
  • Send a single quote ' in each. A database syntax error, or a different response from normal input, shows the text is reaching the SQL.
  • Send x' OR '1'='1 as the department. If you get more rows than a normal request, the value is being treated as SQL.
  • For sort_by, send an expression instead of a column name and compare the ordering to normal input. Different behavior means the text is part of the query.
  • For second-order cases, store a value with quotes and SQL text in a name, then trigger the job that reads it, and check that nothing unexpected runs.
  • After the fix: values must be bound, unsupported sort options must be rejected, and legitimate names like Director's Report must still work.
  • Add regression tests for each case, and search the code for execute( calls that build the query with f-strings, % formatting or +. Static analysis tools such as Bandit flag many of these.
  • Limit the damage if something slips through: give the application's database role only the access it needs. This does not prevent injection, but it limits what injection can do.

Summary

  • SQL injection happens when input becomes part of the command. Keep commands and data separate.
  • Values go in placeholders. Identifiers (column and table names, sort direction) cannot, so map user choices to an allowlist you control.
  • A security fix that breaks the feature, like ORDER BY %s, will be reverted. Check that the fix works as well as that it is safe.
  • Stored data is still untrusted. Second-order injection is stopped by using placeholders at every query that uses the data, not by cleaning it on the way in.
  • A stored procedure is only as safe as the SQL inside it. SECURITY DEFINER raises the impact, so set search_path, limit who can run it and keep the owner's rights small.
  • Injection fixes and access control are separate jobs. Do both.
